# Phase 3b — Kiosk Android UI Redesign

> **⚠️ ABANDONED (2026-07-07) — the kiosk plan has changed.** Do not hand this to Codex and do not use it as a reference for new kiosk work. Left in place as historical record only (including `design-reference/`). See `docs/multi-app-ecosystem/README.md` for current status.

> Part of the [Multi-App Ecosystem Plan](../multi-app-ecosystem-plan.md). This document is self-contained — implement from this file directly.

**Depends on:** Phase 3 (Kiosk Android Migration) in principle — restyling assumes a stable networking/behavior baseline. **By explicit decision, this phase runs in parallel with Phase 3's outstanding review** rather than waiting for it to close first. Accepted tradeoff: if Phase 3's eventual review requires a structural fix to a screen this phase has already restyled, that screen's restyle may need reapplying — bounded rework, not a correctness risk, since Phase 3's code already compiles today. **Blocks:** nothing. **User-facing surface:** every screen in `apps/virtual-tryon-mobile&kiosk` changes visually. No screen is added, removed, or reordered; no navigation path, network call, or business-logic behavior changes.

**Background/color decision (confirmed, do not relitigate):** the current app puts a full-bleed colorful background image (`screen_bg`) behind every screen. This phase replaces that with a neutral white/near-white default background on all screens, reserving the brand gradient and saturated color for CTAs, selected states, badges, and hero/splash moments only — exactly as shown in `design-reference/`. This is a deliberate legibility/premium-feel choice, not an oversight; do not restore the all-over colorful background on any screen.

## Why

The kiosk app's current UI (Material Components v1, XML Views, ad-hoc per-screen drawables, a 40-color palette with no semantic naming, mixed raster/vector icons) works but doesn't read as a premium product. This phase is a **restyle-in-place**: reskin colors, typography, spacing, iconography, component chrome, and motion into one consistent, modern design system — without touching navigation, Activity/Fragment structure, ViewModels, camera/ML pipeline, or any network call. If a screen's visual goal cannot be hit without restructuring its ViewGroup hierarchy, that specific screen is the exception, not the rule — flag it in the Report Back rather than restructuring everything preemptively.

**Three decisions already made (do not relitigate):**
- **No migration to Jetpack Compose.** Compose is a *UI toolkit* (Kotlin-function-based screen building, replacing XML inflation) — adopting it means rewriting every screen's implementation. Leave the Compose dependencies in `build.gradle.kts` unused. Restyle the existing `View`/`ViewBinding`/XML-layout system in place.
- **Yes to migrating the theme parent to Material 3 XML themes.** Material 3 is a *design system* (color roles, shapes, typography, component defaults), independent of Compose — it ships `Theme.Material3.*` XML themes that work directly with `View`/`ViewBinding`, no Compose required. Migrate `Theme.AiVastra`'s parent from `Theme.MaterialComponents.DayNight.NoActionBar` to a Material 3 equivalent (see §1). This is the primary lever for making the app look like a current, premium product rather than a 2019-era Material app with custom paint on top — do this before hand-rolling a parallel token system on the old design system.
- **No ConstraintLayout migration.** ConstraintLayout 2.2.1 is a declared dependency but no layout uses it (`RelativeLayout`/`LinearLayout` throughout). Do not convert layouts to ConstraintLayout as part of this phase — that's a structural change with no visual payoff and real regression risk on 41 layout files. Restyle within the existing ViewGroup types.

**Read before touching anything:**
- `apps/virtual-tryon-mobile&kiosk/app/src/main/res/values/themes.xml` and `colors.xml` — the full current theme and palette.
- `apps/virtual-tryon-mobile&kiosk/app/src/main/res/layout/ll_toolbar.xml` — the one shared include already reused everywhere; get this right once.
- Every layout under `res/layout/activity_*.xml` and `res/layout/item_*.xml` (41 files, listed in full below) before restyling it — this is real, working production code serving a live kiosk fleet.
- Grep every Kotlin reference to a color/dimen/style resource you plan to rename (`ContextCompat.getColor`, `R.color.*`, `R.style.*`, `R.dimen.*`) before renaming it. ViewBinding means widget-class changes (e.g. `Button` → `MaterialButton`) are generally safe, but any code that calls a type-specific method (not inherited from `View`/`TextView`) on a binding field will break at compile time — that's exactly what the typecheck/compile step in the Definition of Done exists to catch.

## Current state (confirmed by direct inventory — do not re-derive)

- **21 Activities + 1 Fragment**, all XML-View-based, ViewBinding + DataBinding both in active use.
- **41 layout files**: 20 Activity layouts, 9 RecyclerView item layouts, 7 dialog/modal layouts, 5 reusable includes (`ll_toolbar.xml`, `ll_loading.xml`, `ll_swipe_animation.xml`, `loader_overlay.xml`, `focus_ring.xml`).
- **Theme**: `Theme.AiVastra` parents `Theme.MaterialComponents.DayNight.NoActionBar`. No `styles.xml`/`dimens.xml` files exist separately — everything lives in `themes.xml`, and spacing uses the `sdp-android` library (`@dimen/_XXsdp`) instead of a defined spacing scale.
- **Palette**: `colors.xml` has 40+ colors, named by appearance not role (`purple`, `teal_700`, `sky`, `parrot_green`, `dark_brown`, five `gradiant*` variants, plus a full set of black/white/gray opacity variants). No semantic tokens (`colorPrimary`, `colorSurface`, `colorOnSurface`, etc. are unused as MDC attributes — everything is a direct hardcoded color reference in layouts).
- **Typography**: Poppins family already bundled (`popins_regular/medium/bold/extrabold/black.ttf`) plus a decorative `jersey_regular.ttf`, applied ad hoc per-`TextView` via `android:fontFamily` + a manually chosen `textSize`. No defined type scale or `TextAppearance` styles.
- **Icons**: 21 vector XML icons (all flat white, no theming), but 70 raster PNG/JPG/WEBP assets mix genuine UI chrome (`ic_back.png`, `ic_search.png`, `icon_menu.png`, `ic_like.png`, `ic_delete.png`, `ic_download.png`, `icon_profile.png`) with real photographic/brand content (background photos `screen1-8.jpg`, pose-guide photos, model photos, logos).
- **Components**: some `MaterialCardView`/`ShapeableImageView`/Material dropdown usage already present, but most buttons and containers are plain `Button`/`ImageView`/`RelativeLayout` with bespoke shape-drawable backgrounds (`bg_cat_item_border_purple.xml`, `btn_background_corner.xml`, etc.) rather than shared `Widget.*` styles.
- **Motion**: 6 `res/anim/*.xml` transition animations (fade/scale/slide, used via `overridePendingTransition`), 7 Lottie JSON animations (`res/raw/*.json`) for processing/loading states, no shared-element transitions, no Jetpack Navigation.
- **Corner-radius styles already defined** in `themes.xml`: `RoundedCorners` (16dp), `SpecificCornerCut` (20dp, top-left+bottom-right cut), `SpecificCornerCutImage` (15dp), `SpecificCornerCutEditText` (10dp) — these are an existing, deliberate brand shape language (cut corners as a visual signature). **Preserve the cut-corner motif** — don't flatten it to plain rounded rectangles everywhere; it's one of the few pieces of intentional visual identity already in the app.

## Spec

### 1. Design tokens (new/rewritten resource files)

Pin actual values now rather than leaving the scale as structure-only — two different implementers should not be able to produce two different-looking apps from this document.

- **`res/values/colors.xml` — full rewrite to semantic naming**, layered in two tiers:
  - Tier 1, brand primitives (keep the actual hex values already carrying brand identity, just renamed): `brand_purple` (`#9e41e2`, was `purple`), `brand_pink` (`#ca3669`, was `red`/pink), `brand_gradient_start` (`#f5881e`, was `gradiant1`), `brand_gradient_mid` (`#cc30dc`, was `gradiant2`), `brand_gradient_end` (`#a803e5`, was `gradiant3`), `brand_success` (`#11cc17`, was `parrot_green`).
  - Tier 2, semantic roles, referencing tier 1: `color_primary` = `brand_purple`, `color_on_primary` = `#FFFFFF`, `color_secondary` = `brand_pink`, `color_surface` = `#FFFFFF`, `color_surface_variant` = `#F3EDF7`, `color_on_surface` = `#1B1420` (new — nothing this dark/neutral exists today; needed for legible body text on a white/light surface), `color_on_surface_variant` = `#6E6470` (new, for secondary/caption text), `color_background` = `#FFFFFF` (default screen background — see call-out below), `color_background_brand` = `#fceaf7` (the existing `app_theme_color`, reserved for splash/marketing-flavored screens only, not the default everywhere), `color_border` = `#EBEBEB` (was `light_gray`), `color_success` = `brand_success`, `color_error` = `#D64550` (**new — no error color exists in the current palette at all**; needed for form validation / failure states and should have existed already), `color_overlay_scrim` = the existing `black_50`.
  - **Design call-out, not just renaming:** the current app uses `app_theme_color` (`#fceaf7`, light pink) as the background on most screens. A saturated tint behind every content-heavy screen (grids, lists, forms) reads as dated rather than premium — modern SaaS surfaces default to a neutral white/near-white background and use brand color only in accents, gradients, and CTAs. Recommendation: switch the default `color_background` to neutral white and keep the pink tint (`color_background_brand`) for splash/hero moments only. Flag in the Report Back if you disagree or find a reason to keep the tinted background everywhere.
  - This is a mechanical, repo-wide rename — grep for every old color name (`@color/purple`, `@color/teal_700`, `@color/sky`, etc.) across all `.xml` and `.kt` files and update every reference in the same commit. Do not leave both old and new names defined "for compatibility" — that's exactly the kind of drift this rewrite is meant to remove.
- **New `res/values/dimens.xml`** — a spacing/radius/elevation scale, expressed via the existing `sdp` unit (don't introduce a second sizing system): `spacing_xs` (`@dimen/_4sdp`), `spacing_sm` (`_8sdp`), `spacing_md` (`_16sdp`), `spacing_lg` (`_24sdp`), `spacing_xl` (`_32sdp`); `radius_sm` (`_10sdp`, matches existing `SpecificCornerCutEditText`), `radius_md` (`_15sdp`, matches `SpecificCornerCutImage`), `radius_lg` (`_16sdp`/`_20sdp`, matches `RoundedCorners`/`SpecificCornerCut`) — the new scale codifies numbers already in use rather than inventing new ones; `elevation_card` = `2dp`, `elevation_dialog` = `8dp` (Material defaults).
- **New `res/values/type.xml`** — `TextAppearance.AiVastra.*` styles, each pinning a Poppins weight + size + line-height:
  - `Display` — `popins_extrabold`, 32sp / 40sp line height
  - `Headline` — `popins_bold`, 24sp / 32sp
  - `Title` — `popins_bold`, 20sp / 28sp
  - `Body` — `popins_regular`, 16sp / 24sp
  - `Label` — `popins_medium`, 14sp / 20sp
  - `Caption` — `popins_regular`, 12sp / 16sp
  - Replace ad hoc `fontFamily` + `textSize` pairs on individual `TextView`s with `android:textAppearance="@style/TextAppearance.AiVastra.*"` references.
- **`res/values/themes.xml` — Material 3 migration**: change `Theme.AiVastra`'s parent from `Theme.MaterialComponents.DayNight.NoActionBar` to `Theme.Material3.DayNight.NoActionBar` (or the fixed-light variant per §5's dark-mode decision), and map the tier-2 semantic colors from §1 onto the real M3 theme attributes (`colorPrimary`, `colorOnPrimary`, `colorSecondary`, `colorSurface`, `colorSurfaceVariant`, `colorOnSurface`, `colorOnSurfaceVariant`, `colorError`, `colorOutline`) so Material components (ripples, tonal elevation, default `MaterialButton`/`MaterialCardView`/`TextInputLayout` styling) pick up the new system automatically instead of every screen re-specifying colors by hand. Before committing to this, spot-check the app's existing custom drawables and `ShapeableImageView`/`MaterialCardView` usages against M3's default shape/elevation changes — if a specific screen visibly breaks under the M3 defaults, override that screen's style locally rather than abandoning the theme migration for the whole app. Keep `RoundedCorners`/`SpecificCornerCut*` styles as-is (still needed, still the brand shape signature) but document what each is for with a one-line comment, since currently nothing explains why there are four near-identical corner styles.
- **New `Widget.AiVastra.*` styles** in `themes.xml` (or a new `res/values/widgets.xml`): `Widget.AiVastra.Button.Primary`, `Widget.AiVastra.Button.Secondary`, `Widget.AiVastra.Card`, `Widget.AiVastra.TextInputLayout`, `Widget.AiVastra.Toolbar`. Apply the appropriate `Widget.AiVastra.*` style to every plain `Button`/`ImageView`-as-button/`RelativeLayout`-as-card in every layout, replacing bespoke per-screen drawable backgrounds where the new shared style covers the same visual (don't force it where a screen genuinely needs a one-off treatment — but audit for the common case, which the inventory suggests is most of them).
- **CI/lint guard against regression**: add a Biome-equivalent guard for Android — either an Android Lint custom rule or a simple repo script (grep-based is fine) that fails CI if a layout XML contains a raw `#RRGGBB`/`#AARRGGBB` color literal or a raw `sp`/`dp` text-size literal outside the token files themselves. Without this, the new token system decays exactly the way the old one did — nothing currently stops the next screen added from hardcoding `#9e41e2` again. This only needs to run in this app's own CI/build step, not the monorepo-wide `pnpm lint`.

### 4. Motion

Keep the existing 6 `anim/*.xml` transitions and 7 Lottie animations — do not rebuild the animation system. Where you touch a screen's transition, standardize on the durations/interpolators already established in the codebase (`fade_and_scale_in/out`, `decelerate_quad` easing) rather than inventing new timing per screen. If a Lottie animation's baked-in colors visibly clash with the new palette, recoloring via Lottie's dynamic-color API (already supported by the `lottie` 6.4.0 dependency, no new library needed) is in scope; re-authoring the animation itself is not.

### 5. Dark mode — explicit decision required

`Theme.AiVastra` currently parents `.DayNight`, but this app runs on **fixed, wall/counter-mounted kiosk tablets** an in-store operator does not toggle system dark mode on. Maintaining and QA-ing two visually distinct theme variants for a device nobody switches doubles the design/test surface for no user benefit. **Decision: drop `.DayNight`, parent a single fixed (light) theme, and set `android:forceDarkAllowed="false"` on the application** so no screen is subject to Android's automatic dark-mode content inversion regardless of the tablet's system setting. If you find a concrete reason kiosks in the field actually do need a dark variant (e.g. dim-store-lighting requirement noted by ops), stop and flag it in the Report Back instead of building it speculatively.

### 6. Accessibility and kiosk ergonomics (do not skip — not optional polish)

This is a **wall/counter-mounted retail tablet viewed at arm's length in variable store lighting**, not a phone held close in a controlled environment — apply a higher bar than generic phone-accessibility minimums, not just the minimums:

- Every icon-only `ImageView`/`ImageButton` gets a non-empty `contentDescription`.
- Touch targets: 48dp is the phone-accessibility *floor*, not the kiosk-comfort *target*. For primary actions a shopper taps directly (capture, try-on, like/cart, category selection), size for a stand-back, imprecise-tap context — treat 56–64dp as the working target for primary actions, 48dp minimum only for secondary/dense controls.
- Legibility at distance: body text sized for a phone held at 30cm reads small at arm's length on a mounted tablet. Re-check the `Body`/`Label` sizes in §1's type scale specifically against this use case during Stage A review, not just against a phone-design instinct.
- Contrast under retail lighting: confirm text-over-photo screens (backgrounds `screen1-8.jpg`, model/pose-guide photos) keep sufficient contrast against bright store lighting and glare, not just against a controlled screenshot — add or adjust `color_overlay_scrim` usage where new smaller/lighter text would otherwise be unreadable over a photo background.

### 7. Performance (explicit requirement — this was the top ask, not a side effect of restyling)

Restyling touches every layout anyway, so treat this pass as a chance to fix real rendering cost, not just repaint colors:

- **Overdraw**: several screens nest `RelativeLayout`s with a full-bleed background image plus additional opaque layers on top. While restyling a screen, flatten unnecessary overlapping opaque backgrounds where the new visual doesn't need them — check with GPU overdraw debug (`Settings > Developer options > Debug GPU overdraw`) before/after on at least the four Stage A screens.
- **Image decode cost**: audit the 70 raster assets for size — several backgrounds/photos are likely larger than their display size ever needs. Downsample or re-export oversized source images; ensure Glide (already the primary image loader) is given target dimensions (`override()`/`ViewTarget` sizing) rather than decoding full-resolution images into small `ImageView`s, especially in the grid/RecyclerView screens.
- **RecyclerView item layouts**: while restyling `item_vastra*.xml`, keep view-hierarchy depth flat — don't add wrapper `ViewGroup`s for the new card styling if a `MaterialCardView` alone (with the new `Widget.AiVastra.Card` style) can hold the same content without an extra nesting layer.
- **Placeholder/loading state**: add a Glide placeholder (solid `color_surface_variant` or a simple shimmer) for grid images instead of blank space during load — perceived speed, not just actual speed.

### 8. Automated visual regression (in addition to manual screenshots)

Manual screenshots of "at least" a handful of screens (Definition of Done) won't catch a silent break on one of the other ~30+ layouts. Add screenshot-diff testing via **Roborazzi** or **Paparazzi** (either runs on the JVM, no emulator required, and neither is a new heavyweight dependency relative to what "restyle 41 layouts by hand" already risks) covering every Activity/Fragment layout touched in this phase. Generate baseline snapshots at the end of Stage A (post-approval) and re-verify them stay intentional through Stage B — a failing snapshot in Stage B means an unintended regression, not a new intentional change, since Stage B is supposed to be mechanical rollout of an already-approved pattern.

## Out of scope for this phase

- No Compose migration, no ConstraintLayout migration (see "Why").
- No change to any network call, ViewModel, Repository, camera/ML pipeline, or Activity navigation graph — if a `.kt` file outside a layout/style/color/dimen resource needs to change, it should only be because a widget class changed (e.g. `Button` → `MaterialButton`) and a call site needs updating to compile, not because behavior is changing.
- No re-encoding of video assets, no re-authoring of Lottie animation content (recoloring via the dynamic-color API is allowed; rebuilding the animation is not).
- No new UI screens, no removed screens, no reordering of the existing flow.
- No app icon/launcher icon change — that's a store-listing/brand asset decision outside this phase's scope; flag if you think it should change, don't just change it.
